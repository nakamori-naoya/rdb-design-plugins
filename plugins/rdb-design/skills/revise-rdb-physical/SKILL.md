# RDB物理設計を改訂する

読み終えると、既存物理設計の根拠と現在の入力・観測を比較し、成立しなくなった型、制約、index、transaction、配置、容量・運用判断を改訂して同じpathへ保存できる。新しい物理資料は作らず、論理データモデル資料や全体基盤構成も変更しない。

同じdirectoryの`playbook.yml`が工程順の定義である。手順に入る前に、同梱の内部skill `physical-design`の`SKILL.md`を読み、その判断規律とtool契約を全工程へ適用する。

## 入力

`design-rdb-physical`が受ける入力に加え、次を受ける。

| 入力 | 内容 | 満たさないときの扱い |
|---|---|---|
| `existing_physical_document_path` | 必須。更新する既存の`rdb-physical-design`型の資料の絶対path | 無い、相対path、読めない、symlink、別pathへの出力要求なら止まる |
| `database_product` / `database_version` | 既存設計を評価する対象。製品・版を変える依頼では新しい対象 | 既存資料から一つに読めず、依頼にも無ければ`challenge-physical-design`で確かめる。決まらなければ止まる |
| `evidence_paths` | 実行計画、benchmark、競合・障害・復旧試験、運用観測 | 証拠が無い論点は机上反証として扱い、実証済みにしない |

その他の要求・負荷・品質・基盤・参照pathは、初回設計と同じ契約で受ける。保存先入力は受け取らず、既存の物理設計資料と同じpathだけを更新する。

## 判断基準

| 観察対象 | 述語 | 行動 |
|---|---|---|
| 変更された入力 | 既存設計の根拠、閾値、分布、基盤制約、DBMS挙動を変える | 影響する判断と検証を再実行する。影響しない節を形式のために書き換えない |
| 観測結果 | 設計時の仮説または完了条件を満たさない | 原因に対応する物理判断を改訂し、観測条件と差分を根拠に残す |
| 競合・障害ケース | 許してはいけない結果、Read鮮度、復旧条件を破る | transaction、制約、retry、replica利用、復旧手順を再設計する |
| 論理モデルとの差 | 業務意味または不変条件そのものの変更を要求する | 物理設計資料を変更せず、論理側へ必要な変更と根拠を返して止まる |
| 改訂先 | 既存の物理設計資料と同じ実体を指す | 更新する。別pathなら新規作成へ切り替えず止まる |

## 手順

1. **preflight-inputs（`scripts/input_paths.py`）。** 全pathをJSONで標準入力へ渡し、絶対pathの通常fileとして読めることを検査する。終了code 0以外なら既存の物理設計資料を変更しない。
2. **challenge-physical-design（`grill`）。** 答えで既存物理判断が変わる未決だけを、観測された差、負荷・品質・基盤の変更、DBMS・版変更に結び付けて渡す。返った未決は推奨を仮説として保持する。
3. **ground-changes。** 既存設計時の根拠と現在入力を比較し、変更なし、確認済みの変更、仮説、未確認、観測結果へ分ける。
4. **revise-and-verify（`physical-design`）。** 内部skillの判断規律で影響する設計を反証・改訂し、未実測を実証済みにせず、完成本文を検査する。
5. **guard-update（`scripts/update-guard.py`）。** 既存の物理設計資料と`requested_output_path`が同じ実体を指すことを検査する。終了code 0が返す`update_target`以外へは保存しない。
6. **update-document（`write-doc`）。** 検査済み本文を`document_type: rdb-physical-design`と`update_target`で保存する。`status: completed`かつ返却pathが`update_target`と一致した場合だけ完了する。

## 停止条件

**止まる。** 必須の入力資料または対象RDB・版を確定できない、path入力が契約に反する、反証対象となる既存物理設計がない、別pathへの保存を求められた、toolまたは外部playbookが失敗する、論理意味の変更が必要になる場合である。既存の物理設計資料を変更せず、確定済み範囲と再開条件を返す。

**仮説を明示して進む。** 実測が無い、観測条件が不完全、複数の改善案が成立する場合は、現在の根拠で最も筋の良い案を仮説として採り、採らなかった案、検証計画、rollback条件、見直し条件を残す。

## 出力

- `updated_physical_rdb_design_path`: 同じpathへ更新したRDB物理設計資料の絶対path
- `status`: `ready`または`unresolved`
- 変化した入力、反証された判断、採用・撤回した物理写像、観測済み／未検証の範囲、論理側または基盤側へ返した事項の報告
