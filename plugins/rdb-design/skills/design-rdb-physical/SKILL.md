# RDB物理設計を作る・見直す

論理データモデルが決めた業務の意味と不変条件を保ったまま、それを対象のRDB製品と版の実現へ写し、判断ごとに根拠と検証状態を持つ物理設計資料を作る。既存の物理設計を渡されたら、同じ判断で見直し、同じパスの資料を更新する。論理データモデル、品質の閾値、負荷の値、全体のクラウド構成は、この入口では作り直さない。

## 判断の要

**業務の意味を変える必要が出たら、物理で補わずに論理へ差し戻す。** 業務上の対象、関係、多重度、履歴、取消や訂正、不変条件を変えなければ実現できないと分かったら、物理設計に書かず、要る論理の変更と根拠を返して止まる。対象のDBMSで実現しにくいことは、論理の意味を変える理由にならない。

**導いた値を保存するのは物理の判断で、理由と整合の保ち方を添える。** 論理データモデルは、起きた事実と業務が与えた値しか持たない。件数、合計、平均、別の見方へ組み替えた一覧を、性能や制約のために保存すると決めるのは物理設計である。保存するなら、どの事実から導くか、同期の契機と失敗時の扱い、作り直し方、要らなくなったときの外し方を書く。書けないなら採らない。詳しくは [references/physical-mapping.md](references/physical-mapping.md) に従う。

**Read を先に決め、それを支える index だけを採る。** 読み取りは、利用者の問い合わせだけでなく、背景処理が要求を回収する走査、監視の集計、条件付き書き込みの判定（`INSERT … SELECT … WHERE NOT EXISTS` など）も含める。利用者に見えなくても、件数とともに遅くなるからである。index は、Read か制約を支えるものだけにする。

**分離レベルと再試行は、物理設計が操作ごとに一つに決める。** 論理データモデルの「同時に進んだときに許されない結果」から、操作ごとに分離レベル、制約、ロック、競合の検出と、transaction の中で直列化の失敗やデッドロックを何回まで繰り返すかを決める。実装はここで決めた指定を渡すだけにする。判断の進め方は [references/transaction-isolation.md](references/transaction-isolation.md) に従う。

**実機の証拠が無い判断は planned にする。** 公式の仕様は機能があることを支えるが、その負荷での性能や競合の結果は示さない。実行計画、benchmark、競合試験、復旧試験、運用観測が対象の条件と結び付くときだけ `verified` にし、それ以外は `planned` として、確かめ方と見直す条件を添える。対象の版の公式資料か実機の結果に届かない機能は採らず、代わりの案か未決にする。

入力の一部（負荷、品質、基盤、実測）が無いときは、最も筋の良い案を仮説として採り、採らなかった案、確かめ方、見直す条件を残して進む。論理データモデル、対象のDBMSと版、保存先が決まらないときは止まる。どちらになるかは、欠けた情報が物理設計の結論を変えるかで決める。

## 入力

論理データモデル資料の絶対パス（必須）、対象のDBMSと一つに決まる版（必須）、新しく作るなら保存先のディレクトリと `.md` の名前、見直すなら既存の物理設計資料の絶対パスを受け取る。要求、利用負荷モデル、品質要求、クラウド構成の各資料と、実行計画や試験の結果は、あれば絶対パスで受け取り、書き換えずに根拠として使う。

## 進め方

1. 入力の資料を読み、事実、合意した決定、仮説、未確認、観測結果に分ける。見直しでは、既存の物理設計を作ったときの根拠と今の入力を比べ、変わったものだけを反証の対象にする。変わっていない節は書き換えない。
2. 調べても分からず、答えで DBMS と版、整合性、容量、配置が変わる問いがあれば、grill で利用者に確かめる。
3. 業務制約を物理制約へ写し、物理写像、型と時刻、Read、index、transaction、配置、容量と運用、採用する機能を決める。論理のテーブルと物理のテーブルを一対一にそろえる必要はない。BDD と論理のテーブル定義は写さず、論理データモデル資料を参照する。
4. write-doc に `document_type: rdb-physical-design` で渡して保存する。新しく作るなら `output_directory` と `name`、見直すなら既存の資料を `update_target` にする。
5. 保存した資料に `python3 scripts/physical_design.py --model-file <論理データモデル資料> --design-file <保存した物理設計資料>` を一回かける。物理制約の表の制約名の集合が、論理データモデルの業務制約の名前の集合と食い違えば、足りない側を直して保存し直す。

## 出力

保存した物理設計資料の絶対パスと、`planned` や未決が残るかを返す。あわせて、論理側またはクラウド構成の側へ差し戻した事項を報告する。
