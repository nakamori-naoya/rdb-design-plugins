# RDB 物理設計の資料に共通する条件

この条件は、実行の担当が design-rdb-physical で作った RDB 物理設計の資料（以下、資料）と grill の記録（以下、記録）を判定するためのもので、どのお題のどのコマンドデータモデルから作ったものにも当てる。ケースに固有の条件は、この後ろに続く。条件は判断の型だけを書き、正しい資料の中身は書かない。どの条件も、ほかの条件の出来、文体、見出しの形では判定しない。各条件の「重み」は点数にまとめるときの値で、判定の厳しさは変えない。重み3は利用者の原則の芯（推測で埋めない、一つの判断は一か所が持つ、データと情報を分ける、業務の意味を物理で変えない）、重み2は資料の骨組み、重み1は細部である。資料や記録が存在しない、または空のときは、それを読む条件はすべて FAIL とする。

実行の担当は、コマンドデータモデル、クエリデータモデル、業務知識の資料と、要件（要求、利用規模と負荷、非機能要件）を渡された。要件は system-design の資料の形にはなっていない。対象の DBMS と版は依頼で指定された。grill の問いには、渡した資料から決まることで答え、決まらなければ問いに添えた推奨を仮置きして資料の未決に書くよう指示されていた。

## 業務の意味を物理で変えない

### meaning-send-back

重み: 3

PASS：資料は、コマンドデータモデルの業務上の対象、関係、多重度、履歴、不変条件を変えずに写している。物理だけでは実現できず業務の意味の変更が要ると判断したことは、物理設計に書き込まず、コマンドデータモデルへの差し戻しとして、要る変更と根拠を添えて資料か報告に書いている。差し戻しが無いなら、無いことが読み取れる。

FAIL：コマンドデータモデルに無い業務の決まりを物理の側で足している、コマンドデータモデルの決まりを物理の都合で緩めている、またはコマンドデータモデルのテーブルの意味を変える列やテーブルを差し戻しなしに置いている。根拠の欄に、その箇所と、コマンドデータモデルの該当箇所を書く。

### meaning-derived-values

重み: 3

コマンドデータモデルにない、事実から導ける値（件数、合計、最新の一件、別の見方へ組み替えた一覧、キャッシュ、投影、集計の表や列）を資料が保存すると決めた箇所を、一つずつ挙げて確かめる。

PASS：挙げた箇所のすべてに、どの事実から導くか、一次データはどこか、同期の契機と失敗時の扱い、作り直し方、要らなくなったときの外し方が書かれている。コマンドデータモデルに無い表か列を足したなら、どの業務の操作で何行が、各列のどの初めの値で変わるかも書かれている。書けないものは採らず、未決に置いている。保存すると決めた箇所が無ければ PASS とする。根拠の欄に、挙げた箇所と、欠けている項目を一覧で書く。

FAIL：導ける値を保存すると決めたのに、上の項目のどれかが欠けている箇所が一つでもある。

### meaning-constraint-mapping

重み: 2

PASS：物理制約の表は、コマンドデータモデルの業務制約の一つひとつを、どのテーブルと列に、対象の DBMS のどの機能で、いつ、違反したら何を返すかで写している。一行の制約で守れない制約（件数の上限、まだ無いことを根拠にする判断など）は、制約の表で済ませたことにせず、分離性の判断と結び付けている。

FAIL：業務制約に対応する行が無い、実現方法が対象の DBMS の機能として読めない、または一行の制約で守れない制約を一意制約や CHECK だけで守ったことにしている。

### meaning-check-owner

重み: 2

PASS：業務の値の正しさ（値域）を CHECK で守るかどうかを、その値を書くのがドメインモデルだけかで分けている。ドメインモデルだけが書く業務のテーブルに値域の CHECK を置かず、ドメインモデルの外から書かれるテーブル（技術処理の表、取り込み、運用の手作業）には置いている。主キー、一意、外部キー、版の条件付き更新はどの表にも置いてよい。

FAIL：ドメインモデルだけが書く業務のテーブルに値域の CHECK を置いている、または技術処理の表の値域をどこでも守っていない。

## 分離性と再試行

### isolation-per-operation

重み: 3

コマンドデータモデルの同時に進む場面（並行実行で必要な保証、同時の BDD）を一つずつ挙げて確かめる。

PASS：挙げた場面のすべてについて、同時に進む二つの判断のあいだで許してはいけない結果が書かれ、それを防ぐ分離レベル、制約、ロックのどれを使うかと、トランザクションの中で直列化の失敗やデッドロックを何回まで繰り返すかが、操作ごとに一つに決まっている。実装に選ばせる書き方（「実装で適切に」「必要に応じて」）をしていない。根拠の欄に、挙げた場面と、決めた手段と回数を一覧で書く。

FAIL：分離レベルか繰り返しの回数が決まっていない操作がある、決めることを実装やほかの資料へ回している、または分離レベルの名前だけで、誰のどの判断がどう誤るかが書かれていない。

### isolation-absence-rule

重み: 3

まだ無いことを根拠にする判断（件数の上限、重複の禁止のように、確かめた時点に行が無いことで成り立つ判断）が、コマンドデータモデルにあるかを確かめる。

PASS：そうした判断のそれぞれについて、行の競合だけでは防げないことを踏まえ、重なりを拒む制約、SERIALIZABLE と繰り返し、集計の列、調整用の行のどれで守るかを比べて選んでいる。集計の列か調整用の行を採るなら、それが業務の事実でないことと、元の事実との整合の保ち方を書いている。該当する判断が無ければ PASS とする。

FAIL：そうした判断を、行の版の検査や READ COMMITTED の一行の更新だけで守れるとしている、または守り方が書かれていない。

### isolation-external-outside

重み: 2

PASS：外部への通信（配信、通知、外部サービス）と人の応答を待つ部分を、トランザクションの外に置いている。要求を回収する操作は、回収の事実を足す短いトランザクションにし、同じ要求を二つの担い手が同時に回収しないことをどう守るかを書いている。技術処理の要求が無いデータモデルなら PASS とする。

FAIL：外部への通信をトランザクションの中に置いている、または技術処理の回収の重複をどう防ぐかが書かれていない。

## 読み取りと index

### read-before-index

重み: 2

PASS：代表的な読み取りに、クエリデータモデルの BDD が決めた組み合わせと並び順の読み取りが載り、背景処理の走査（要求の回収など）、書き込みの中の判定（件数の上限の確かめなど）も載っている。index はどれも、載っている読み取りか制約を支えるものとして結ばれ、どの読み取りも支える index か、要らない理由を持つ。

FAIL：クエリデータモデルの読み取りか、背景処理の走査か、書き込みの中の判定が載っていない。または、どの読み取りにも制約にも結ばれない index がある。

### read-query-meaning-kept

重み: 2

PASS：キャッシュ、投影、読み取り元の切り替えを採るなら、クエリデータモデルが決めた結果（表示対象、並び順、続きの位置）を変えない範囲で採っている。鮮度の遅れを許すかどうかは、要件か品質要求の根拠を引いて決めている。

FAIL：読み取りの結果（表示対象、並び、件数の区切り）をクエリデータモデルと違う形に変えている、または根拠なしに鮮度の遅れを許している。

## 推測で埋めない

### evidence-planned

重み: 3

PASS：実行計画、負荷試験、競合試験、復旧試験の結果が無い判断は、すべて planned で、確かめ方と見直す条件が添えられている。公式資料だけに基づく判断を verified にしていない。採った機能には、対象の版で使えることの根拠（公式資料の URL か実機の確認）が書かれている。

FAIL：実機の証拠が無いのに verified と書いた判断がある、または planned の判断に確かめ方か見直す条件が無い。

### evidence-hypothesis-marked

重み: 3

PASS：入力に無かった値（容量、到着率、SLO、基盤の構成など。理由の文、表のセル、見直す条件の閾値に書いた数も含む）や、記録で推奨を仮置きした答えを使った判断は、仮説と分かる語で書かれ、根拠、採らなかった案、見直す条件が添えられている。要件にある値を使うときは、どの文書のどの値かを書いている。要件に無い具体値（件数、時間、回数）を、根拠なしに事実として書いていない。

FAIL：要件に無い具体値や仮置きの答えが、根拠も仮説の断りも無く書かれている。根拠の欄に、その値と箇所を書く。

## 持ち主の境界

### owner-infra-out

重み: 2

PASS：region、可用性ゾーン、ネットワーク、計算資源、マネージドサービス、全体の HA/DR 構成の選定を、この資料で決めていない。基盤構成の資料が無いときは、それを未決か仮説とし、物理設計が扱うのは、複製の遅れ、読み取りの整合性、切り替え中の書き込み、バックアップと復元のような、RDB の整合性と復旧への影響だけにしている。

FAIL：クラウドの製品や全体の構成を、この資料の決定として選んでいる。

### owner-no-copy

重み: 1

PASS：コマンドデータモデルとクエリデータモデルの BDD、ER 図、テーブル定義を写さず、参照している。

FAIL：データモデルの BDD、ER 図、テーブル定義のまとまりを資料に写している。

## 容量と運用

### ops-capacity

重み: 1

PASS：データ量、主要な書き込みと読み取り、バックアップについて、要件の値か仮説の値を、単位と時間窓を添えて設計判断と確かめ方に結んでいる。

FAIL：容量と運用の判断に、単位か時間窓の無い値がある、または確かめ方が無い。

## grill

### grill-only-conclusion-changing

重み: 1

PASS：記録にある問いは、答えで DBMS と版、整合性、容量、配置が変わるものだけで、渡した資料から決まることを問い直していない。問いが一つも無いときは、問わなかった理由が記録か報告にある。

問いが結論に関わるかだけでなく、答えが渡した資料や依頼から既に決まっていたかを、記録に書かれた答えの根拠で確かめる。答えの根拠が資料や依頼の事実だけで、推奨の仮置きも未決も要らなかった問いは、渡した資料から一つに決まることを問うたものとして数える。

FAIL：渡した資料から一つに決まることを問うている問いがある。または、問いが無く、その理由も無い。
