# grill の記録 — フォローのRDB物理設計

design-rdb-physical の進め方2で、調べても分からず、答えで DBMS と版、整合性、容量、配置が変わる問いだけを出した。答える利用者がいないため、依頼の決まりに従って自分で答えた。資料と要件の事実で決まるものはその事実で答え、決まらないものは推奨を仮置きした。仮置きした答えは、物理設計資料の「未決」に、根拠、採らなかった案、確定の条件と一緒に書いた。

## 問わなかった論点と、その前提

次の論点は資料から答えが決まるので、問いにしないで次の前提で進めた。

- `follows` から `users` への外部キーを張れるか: 張れる。利用規模と負荷モデルの「結論」と「採用値ができるまで」が、一次データを単一の AlloyDB（PostgreSQL 互換）に置くとしているので、`users` と `follows` は同じデータベースにある。
- 「自分へのフォローは無い」を CHECK にするか: CHECK にしない。skill の references/physical-mapping.md「値域の CHECK を置く表」によると、ドメインモデルだけが書く業務の表には値の正しさを判定する CHECK を置かない。コマンドデータモデルの「業務知識のBDDとの対応」でも、行を読む前にドメインモデルで拒むとしている。
- `follows` を読むほかの業務の読み取り（ポストの受付時のフォロワー数、配信の範囲の走査、ホームタイムラインのフォロー中の相手）を index の対象に含めるか: 含める。ポストのコマンドデータモデル「ほかの資料が持つテーブル」、ホームタイムラインのクエリデータモデル「ホームタイムラインを読む」、利用規模と負荷モデル「累積データ量」が、`(followee, follower)` の複合 index で走査すると書いている。
- 「フォローする相手を探す」一覧で、一回に返す件数: 問わない。クエリデータモデルの「未決」にあるとおり、API の契約で決める値である。整合性、容量、配置は変わらず、Read-001 の LIMIT の値が変わるだけなので、物理設計の未決として持ち越した。

## 問いと答え（出た順）

### Q1. 対象のDBMSは PostgreSQL 17.6 か、要件にある AlloyDB か

```text
❓ 対象のDBMS: 物理設計は PostgreSQL 17.6 を対象にするか、要件が名指しする AlloyDB を対象にするか
➡️ 推奨: PostgreSQL 17.6 を対象にし、使う機能はコミュニティ版の PostgreSQL 17.6 にあるものに限る。AlloyDB を本番に使うときの互換の版と読み取りプールは、基盤構成の側へ差し戻す
   理由: 依頼が対象の DBMS と版を PostgreSQL 17.6 と指定している。要件は製品の選択を要件ではないとしている（バックエンド要件「技術と開発の制約」）
```

- 答え: 推奨どおり、PostgreSQL 17.6 を対象にする。AlloyDB 固有の機能（列指向エンジン、読み取りプールの遅れの特性）には頼らない。
- 根拠: 依頼文の「対象の DBMS は PostgreSQL、版は 17.6」という事実で決まる。バックエンド要件「技術と開発の制約」には「データベース…の製品選択は、この資料の要件ではない」とあり、非機能要件「移植性と開発環境」によるとローカルでは PostgreSQL を起動する。仮置きではない。
- 物理設計への影響: 本番を AlloyDB にするときに、PostgreSQL 17 との互換の程度と読み取りプールの遅れを確かめる件は、基盤構成への差し戻しとして資料の未決に書いた。

### Q2. フォロー中の上限5,000人を、同時のフォローでも超えないようにする守り方

```text
❓ 上限5,000人の守り方: 同じフォロワーの二つのフォローが同時に進んだときに5,001人目を防ぐ方法として、SERIALIZABLE と、トランザクションの中での再試行を使ってよいか
➡️ 推奨: フォローする操作（初めてのフォローと、またフォローする場合）を SERIALIZABLE で実行し、直列化の失敗（40001）とデッドロック（40P01）を、トランザクションの中で最大3回まで再試行する。フォロー中の人数を列として持たず、フォロー中の行を数える
   理由: 上限は、まだ無い行を根拠にした判断なので、書き込みスキューにあたる（skill references/transaction-isolation.md）。一意制約や排他制約では件数の上限を表せない。その次の候補が SERIALIZABLE である。フォロー変更は設計基準2件/秒、1秒バースト50件/秒で、利用者ごとのレート制限は20回/分なので、同じフォロワーどうしの競合はまれである。人数の列は導いた値を二つ目として持つことになり、利用者ごとの行でロックする案は並行制御の都合を持ち込む
```

- 答え: 推奨を仮置きする（未決）。
- 根拠: 要件には「同時に複数のフォロー要求が進んでも、フォロー中の関係を5,000件以下に保つ」という結果だけがあり（バックエンド要件「フォローできる」）、守り方は書かれていない。競合試験の結果も無い。心配なのは次の点である。フォロー中が多い利用者の人数を数えるとき、PostgreSQL の述語ロックがページ単位からテーブル単位へ格上げされる（既定の設定では、一つのテーブルでページが32を超えると格上げされる）。すると、別の利用者のフォローとのあいだで偽の直列化失敗が増えうる。これは実機で確かめていない。
- 採らなかった案: フォロワーごとの `pg_advisory_xact_lock` を READ COMMITTED と組み合わせる案。ほかに、`users` の行を `FOR NO KEY UPDATE` でロックする案と、フォロー中の人数の列を持つ案。
- 確定の条件: 競合試験で、フォロー中が5,000人に近い利用者を含めて1秒バースト50件/秒を流し、3回の再試行を使い切る割合を測る。0.1%を超えたら、助言ロックの案へ移る。

### Q3. 反映待ちの要求を、累積する要求の中からどう探すか

```text
❓ 反映待ちの探し方: 反映の要求は削除せずに3年で約1億6,400万件たまる。その中から反映待ちの要求を探すために、要求ごとの予定の派生の表（反映待ちか、次に回収できる時点）を物理側に置いてよいか
➡️ 推奨: 置く。要求と同じトランザクションで一行を作り、回収と成功のイベントと同じトランザクションで更新する。反映し終えても行は残し、反映待ちの行だけに部分 index を張る
   理由: 成功の表とアンチ結合して全体を読むと、件数とともに遅くなる。利用規模と負荷モデル「累積データ量」は、ポストの配信について同じ形（要求ごとの調停用の派生の状態と、pending の行だけの次回時刻の索引。完了後も行を残す）を合意している
```

- 答え: 推奨を仮置きする（未決）。
- 根拠: 利用規模と負荷モデル「累積データ量」はポストの配信についての記述で、フォローの反映については書いていない。したがって事実では決まらず、同じ考え方を類推して仮置きした。非機能要件「データの保持」によると Outbox の要求、回収、完了の記録は削除しない。派生の表の行も、完了後に消さず残す。
- 採らなかった案: 派生の表を置かず、要求の表と成功の表をアンチ結合して、古い順に読む案。もう一つは、`FOR UPDATE SKIP LOCKED` で回収候補を取り合う案。
- 確定の条件: 未完了の件数とアンチ結合の実行計画を、実データの件数で測る。未完了が少なくても累計の件数に比例して遅くなるなら、派生の表を確定する。

### Q4. 「フォローする相手を探す」の読み取りを、どのインスタンスから読むか

```text
❓ 一覧の読み取り元: 利用者の一覧に自分から見たフォローの区別を重ねる読み取りを、プライマリから読むか、読み取りの複製（読み取りプール）から読むか
➡️ 推奨: プライマリから読む
   理由: フォローした直後に一覧を開いた本人に、自分のフォローが「フォローしていない」と見えると、二重にフォローしようとして拒まれる。要件は、ホームタイムラインの反映の遅れは許しているが、この一覧の遅れを許すとは書いていない。この一覧の頻度は負荷モデルに無いが、フォロー変更の設計基準は2件/秒と小さい
```

- 答え: 推奨を仮置きする（未決）。
- 根拠: 要件（バックエンド要件「フォローできる」）には一覧の鮮度が書かれておらず、この一覧の頻度も利用規模と負荷モデルに無い。読み取りの複製の構成と遅れは基盤構成の資料にあたるが、その資料は無い。
- 採らなかった案: 読み取りプールから読み、遅れを許す案。
- 確定の条件: 一覧の要求頻度と、読み取りの複製の遅れが分かったとき。頻度がプライマリの負荷として無視できないほど大きいと分かったら、読み取りプールへ移し、書いた本人だけプライマリから読む形を比べる。

「この一覧で対話を終えることに合意しますか」という問いには、利用者の代わりとして合意した。合意の根拠は次の二つである。

- 決定の Q1 は依頼の事実で決まる。
- 未決の三件は、どれも推奨を仮置きしたことと、確定の条件を物理設計資料の未決に書くことにしている。
