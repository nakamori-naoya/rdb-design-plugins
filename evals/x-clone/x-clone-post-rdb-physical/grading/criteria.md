# X のクローンのポストに固有の条件

ポストのコマンドデータモデルは、ポストの事実と、ホームタイムラインへの配信の要求を同じ変更で積み、配信の担い手が要求を回収して、範囲ごとに届け終える形を持つ。要件には、ホームタイムラインのキャッシュ（Redis、500件）、AlloyDB、配信の経路のような製品と方式が多く書かれ、読み取りはポストの100倍ある。この条件は、そこでの判断を型にしたものである。

### post-cache-outside-rdb

重み: 3

PASS：要件にある RDB の外のキャッシュ（Redis のホームタイムラインのキャッシュ）を、RDB の物理設計の決定にしていない。触れるなら、RDB の外の読み取り元として、RDB の側で何を一次データとして返せなければならないか（キャッシュが無いときの作り直し、キャッシュで足りないときの古いポストの読み取り）に絞っている。RDB の中にタイムラインの投影を持つと決めるなら、導く元、同期の契機と失敗時の扱い、作り直し方、外し方を書いている。

FAIL：Redis のキー、容量、退避の方針のような RDB の外の構成をこの資料の決定として書いている。または、RDB の中にタイムラインの投影を、導いた値としての説明なしに持っている。

### post-claim-scan

重み: 2

PASS：配信の担い手が未完了の要求を探す走査を、代表的な読み取りに載せ、ポストが増えても走査が遅くならない index か、その見直しの閾値を書いている。完了した要求を走査から外す方法が、コマンドデータモデルの追加のみの形を変えずに書かれている。

FAIL：未完了の要求を探す走査が読み取りに無い、またはそれを支える index が無い。または、完了した要求を消す、書き換えるなど、追加のみの形を変えて走査を速くしている。

### post-product-as-input

重み: 2

PASS：要件にある AlloyDB と、依頼で指定された PostgreSQL 17.6 の関係を、推測で一つに決めず、仮説か未決として扱うか、依頼の指定を優先した理由を書いている。AlloyDB 固有の機能を採るなら、その根拠を書いている。

FAIL：AlloyDB と PostgreSQL 17.6 の食い違いに触れないまま、どちらかの固有の機能や性質を前提にしている。
