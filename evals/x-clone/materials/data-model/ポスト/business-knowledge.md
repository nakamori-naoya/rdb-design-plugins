# ポストの業務知識

利用者と、このサービスを作り運営する人が、どんな本文ならポストできるか、ポストした後に何が変わらないかを同じ言葉で判断するための業務知識である。ポストの業務は、利用者が本文を書いてポストしたときに始まり、そのポストが生まれたところで終わる。生まれたポストを誰がどこで読むかは、この業務の外にある。

# 概要

ポストの業務は、利用者が自分の言葉を短いプレーンテキストで残し、ほかの利用者が読めるものにする業務である。一件のポストは、一人の投稿者と、1文字以上280文字以下の本文と、ポストIDでできていて、生まれた後は変わらない。読む人が見るのは投稿者が書いたとおりの本文であり、後から書き換わったり、書いた人が入れ替わったりしないことが、読む人と書く人の信頼の土台になる。

ポストはこのプロダクトのコアとして扱う。ホームタイムラインとユーザータイムラインで利用者が読むものはポストだけであり、何がポストとして成り立つかが、読む体験の中身をそのまま決めるからである。

この業務は、ポストを読むことを担わない。自分とフォロー中の相手のポストを読むのはホームタイムラインの業務が、本人または他者のポストの一覧を読むのはユーザータイムラインの業務が担う。利用者として登録し、誰が利用者かを決めるのはアカウントの業務である。ポストの編集、削除、返信、再投稿、メディアの添付は、初期リリースでは扱わない。

## 業務用語

### ポスト

一人の利用者が書いて残した、一件の短いプレーンテキストである。同じ本文を二度ポストしても、二件の別のポストになる。本文が同じかどうかでポストを一つにまとめないのは、利用者が同じ言葉を二度言ったことも、それぞれ一つの発言だからである。

### ポストID

一件のポストを一つに特定する番号である。ポストしたときに決まり、その後変わらない。どのポストかを指すのはこの番号で、本文や投稿者の組み合わせでは指さない。

### 投稿者

そのポストをポストした利用者である。ポストしたときに決まり、ほかの利用者へ移らない。利用者が「誰の」ポストかを判断するときは、この投稿者で判断する。

### 本文

投稿者がポストに書いたプレーンテキストである。受け付けた本文は、前後の空白も含めて、書かれたとおりに残す。読む人が見る本文と、投稿者が書いた本文がいつも同じであるようにするためである。

### 文字数

本文の長さで、Unicode のコードポイントの数で数える。見た目の文字の数とは違うことがある。たとえば、家族を表す絵文字「👨‍👩‍👧」は見た目では1文字だが、五つのコードポイントでできているので5文字と数える。

### 本文の上限

一件のポストの本文の文字数の上限で、280文字である。280文字ちょうどはポストでき、281文字はポストできない。

### 空白

Unicode で空白とされる文字である。半角空白、全角空白、タブ、改行を含む。空白だけの本文は、読む人には何も書かれていないのと同じなので、ポストにしない。空白の範囲をこうしたのは仮説で、根拠は「まだ決まっていないこと」に書いた。

### ポストした日時

投稿者がポストした日時である。いつポストしたかを後から説明するときに使う。新しい順を決めるのには使わない。

### 新しい順

ポストの並びの基準で、ポストIDの大きいものほど新しいとする。ポストした日時の順とは一致しないことがあるが、並びはいつもポストIDで決める。ポストを並べる業務（ホームタイムラインとユーザータイムライン）は、この語を使って並びを決める。

## 業務イベント

### ポストした

利用者が本文を書き、ポストが一件生まれた。ポストID、投稿者、本文、ポストした日時がこのときに決まり、以後変わらない。生まれたポストは、ほかの業務が読める事実になる。

# 概念

## ポスト

ポストは、投稿者が書いたときの本文を、そのまま残した一件の発言である。ポストした時点ですべてが決まり、その後に変わることは無い。だから、ポストは状態を持たず、一件ごとに「ポストした」という一つの事実だけがある。

ポストが成り立つかは、その一件の本文と、ポストしようとしている人が本人の利用者かどうかだけで決まる。ほかのポストの件数や、同じ本文のポストが既にあるかどうかは判断に使わない。

# 常に守られること

### ポストの本文と投稿者は、ポストした後に変わらない

本文が後から変わると、読んだ人が見た発言と今の発言が食い違い、何が言われたかを誰も確かめられなくなる。投稿者が変わると、その発言の責任を誰が負うのかが分からなくなる。

### どのポストの本文も、1文字以上280文字以下で、空白でない文字を含む

この範囲の外にあるポストが一件でもあると、読む人は、何も書かれていないポストや、決めた長さを超えるポストを受け取ることになる。

### 本文は、投稿者が書いたとおりに残る

前後の空白を削ったり、文字を置き換えたりすると、投稿者が意図した見た目と読む人が見るものが違ってしまう。

### 誰が、いつ、どの本文をポストし、それがどの順だったかを、後から説明できる

利用者から「このポストはいつ、どの本文でしたか」「どちらが先ですか」と問われたとき、サービスの運営者は、その利用者のポストを起きた順に示して答える。説明できなければ、利用者の問いに事実で答えられない。説明する相手と目的は仮説で、根拠は「まだ決まっていないこと」に書いた。

# 状態と、その移り変わり

## ポスト

状態を持たない。ポストはポストしたときにすべてが決まり、初期リリースには、ポストを変える行い（編集、削除）が無いからである。

# 業務の行い

## コマンド

### ポストする

登録を終えた利用者が、本人として行える。ほかの利用者としてポストできると、書いていない発言がその人の発言として読まれ、名前を使われた利用者が、自分の言っていないことの責任を問われる。利用者として登録していない人がポストできると、誰の発言かを利用者として示せないポストが生まれる。

本文の文字数が1文字以上、本文の上限の280文字以下で、空白でない文字を一つ以上含むとき、ポストは成り立つ。1文字と280文字はポストでき、0文字と281文字はポストできない。ポストすると、ポストIDが決まったポストが一件生まれ、「ポストした」が起きる。同じ利用者が同じ本文を前にポストしていても、新しい別のポストになる。

ポストの回数の上限（5回/秒、60回/時、300回/日）は、業務の判断ではなく負荷から守るための値なので、非機能要件の負荷保護に置いた。ポストがホームタイムラインに届くまでの時間も、非機能要件の整合性と鮮度に置いた。

#### 拒む理由: ほかの利用者としてポストする

書いていない発言が、その人の発言として読まれてしまう。発言の責任は、書いた本人だけが負う。

#### 拒む理由: 利用者でない人がポストする

利用者として登録していない人のポストは、誰の発言かを利用者として示せない。

#### 拒む理由: 本文に空白でない文字が無い

0文字の本文と空白だけの本文は、読む人には何も書かれていないのと同じで、発言にならない。

#### 拒む理由: 本文が280文字を超える

本文の上限を超えるポストを許すと、短い発言を読み流すというこのサービスの読み方が成り立たなくなる。

## クエリ

なし。ポストを読む行いは、ホームタイムラインの業務とユーザータイムラインの業務が持つ。

# 導出されること

本文の文字数は、本文の Unicode のコードポイントの数である。新しい順は、ポストIDの大小だけで決まる。

# 同時に起きたとき

なし。ポストが成り立つかは、その一件の本文と、ポストする人が本人の利用者かだけで決まり、ほかのポストを判断に使わない。同じ利用者が同時に二件ポストしても、どちらも成り立ち、互いに相手を妨げない。

# まだ決まっていないこと

後から説明する相手と目的は、仮説として「サービスの運営者が、利用者の問いに答えるため」と置いた。要件は、成功したポスト作成について後から事実と順序を説明できることを求めているが、誰が何を説明するためかを書いていない。採らなかった案は「投稿者本人が自分で確かめるため」である。業務の人（要件の回答責任者）に確かめる。

空白の範囲は、仮説として「Unicode で空白とされる文字すべて（半角空白、全角空白、タブ、改行を含む）」と置いた。要件は「空白だけの本文は拒否する」とだけ書いている。採らなかった案は「半角空白だけを空白とする」で、これだと全角空白だけの本文がポストになる。業務の人に確かめる。

空白でない文字のうち、制御文字のように読む人に見えない文字だけの本文を拒むかは決まっていない。要件に制限が無いので、この資料では拒む理由に置かず、受け付けるとしている。拒むと決まれば、拒む理由を一つ足す。業務の人に確かめる。

# BDD

ここまでの決まりが、具体の場面でどう働くかを示す。上で書いていない決まりは持ち込まない。

## ポストする

### [BDD-001] 利用者が本文を書いてポストすると、ポストが一件生まれる

```gherkin
Given: 利用者ID U-0001 の利用者は登録を終えている
  And: 利用者 U-0001 はまだ一件もポストしていない
When: 利用者 U-0001 が本人として、2026年10月1日 10:00に本文「はじめてのポスト」をポストする
Then: 投稿者が U-0001、本文が「はじめてのポスト」のポストが一件生まれ、ポストIDが決まる
  And: 「ポストした」が起き、ポストした日時は2026年10月1日 10:00である
```

### [BDD-002] 1文字の本文はポストできる

```gherkin
Given: 利用者 U-0001 は登録を終えている
When: 利用者 U-0001 が本人として、本文「あ」（1文字）をポストする
Then: 本文が「あ」のポストが一件生まれる
```

### [BDD-003] 280文字ちょうどの本文はポストできる

```gherkin
Given: 利用者 U-0001 は登録を終えている
When: 利用者 U-0001 が本人として、「あ」を280個並べた本文（280文字）をポストする
Then: その本文のポストが一件生まれる
```

### [BDD-004] 281文字の本文はポストできない

```gherkin
Given: 利用者 U-0001 は登録を終えている
When: 利用者 U-0001 が本人として、「あ」を281個並べた本文（281文字）をポストする
Then: ポストは生まれない
  NOTE: Rule: 本文が280文字を超える
    Reason: 本文の上限は280文字である
```

### [BDD-005] 見た目が280文字以下でも、コードポイントで280文字を超える本文はポストできない

```gherkin
Given: 利用者 U-0001 は登録を終えている
  And: 絵文字「👨‍👩‍👧」は見た目では1文字だが、五つのコードポイントでできている
When: 利用者 U-0001 が本人として、「👨‍👩‍👧」を57個並べた本文（見た目では57文字、文字数は285文字）をポストする
Then: ポストは生まれない
  NOTE: Rule: 本文が280文字を超える
    Reason: 文字数はコードポイントで数え、285文字は本文の上限を超える
```

### [BDD-006] 0文字の本文はポストできない

```gherkin
Given: 利用者 U-0001 は登録を終えている
When: 利用者 U-0001 が本人として、何も書かれていない本文（0文字）をポストする
Then: ポストは生まれない
  NOTE: Rule: 本文に空白でない文字が無い
    Reason: 何も書かれていない本文は発言にならない
```

### [BDD-007] 全角空白と改行だけの本文はポストできない

```gherkin
Given: 利用者 U-0001 は登録を終えている
When: 利用者 U-0001 が本人として、全角空白2文字と改行1文字だけの本文（3文字）をポストする
Then: ポストは生まれない
  NOTE: Rule: 本文に空白でない文字が無い
    Reason: 全角空白と改行も空白であり、空白だけの本文は発言にならない
```

### [BDD-008] 前後に空白のある本文は、空白を含めて書いたとおりに残る

```gherkin
Given: 利用者 U-0001 は登録を終えている
When: 利用者 U-0001 が本人として、半角空白2文字、「こんにちは」、改行1文字の順に並んだ本文（8文字）をポストする
Then: ポストが一件生まれる
  And: そのポストの本文は、前の半角空白2文字と後ろの改行1文字を含む8文字のままである
```

### [BDD-009] 同じ本文を二度ポストすると、別のポストが二件になる

```gherkin
Given: 利用者 U-0001 は登録を終えている
  And: 利用者 U-0001 は2026年10月1日 10:00に本文「おはよう」をポストし、ポスト P-0001 が生まれている
When: 利用者 U-0001 が本人として、2026年10月1日 10:01に同じ本文「おはよう」をポストする
Then: ポスト P-0001 とは別のポストIDのポストが、新しく一件生まれる
  And: ポスト P-0001 は変わらない
```

### [BDD-010] ほかの利用者としてはポストできない

```gherkin
Given: 利用者 U-0001 と利用者 U-0002 はどちらも登録を終えている
When: 利用者 U-0002 が利用者 U-0001 として、本文「なりすまし」をポストする
Then: ポストは生まれない
  NOTE: Rule: ほかの利用者としてポストする
    Reason: 発言の責任は、書いた本人だけが負う
```

### [BDD-011] 利用者として登録していない人はポストできない

```gherkin
Given: ある人は Google アカウントで本人確認されたが、利用者としての登録を終えていない
When: その人が本文「こんにちは」をポストする
Then: ポストは生まれない
  NOTE: Rule: 利用者でない人がポストする
    Reason: 利用者として登録していない人のポストは、誰の発言かを利用者として示せない
```
