# 非機能要件

初期リリースのバックエンドが、機能の成立条件とは別に守る性質を一か所に集める。数値は[利用規模と負荷モデル](利用規模と負荷モデル.md)の設計入力と、[バックエンド要件](バックエンド要件.md)で合意した暫定値をそのまま引く。この資料は「何を守るか」だけを書き、実現方式は後続の設計で具体化する。

**機能要件には載らないが利用者が観測する品質上の振る舞い（レート制限による拒否、他者ポストの反映の遅れ、障害時の縮退）は、この資料で定義する。** 業務の成立条件と拒否理由は機能要件が持ち、この資料は品質条件だけを扱う。

## 性能

日間利用者150万人を対象にし、次の設計基準を満たす。1秒バーストは同期処理だけで処理し切るのではなく、非同期経路の滞留で吸収してよい。

| 操作 | 設計基準 | 1秒バースト |
|---|---|---|
| ポスト | 50件/秒 | 500件/秒 |
| ホームタイムライン取得 | 3,500件/秒 | 3万件/秒 |
| フォロー変更 | 2件/秒 | 50件/秒 |

ホームタイムライン取得はポストの約100倍であり、読み取り経路を主要経路として軽く保つ。通常ポストの平均配信先200人とフォロワー数の偏りは縮小しない。応答時間の目標値と負荷試験は初期完了条件に含めない。

## 整合性と鮮度

- 自分のポスト、自分のフォロー変更、他者のポストは、いずれもAPI成功後に非同期処理でタイムラインへ反映する。APIはタイムライン用Redisへ書き込まない。
- 反映できなかった要求は完了扱いにせず、通常のメッセージ処理による再試行と独立した調停処理から、同じ要求IDで再び処理できる状態にする。件数不足や経過時間を理由とする定期的なキャッシュ作り直しには依存しない。
- 設計負荷の範囲では、成功したポストとフォロー変更からタイムラインへ反映されるまでの時間について、99%を5分以内とする運用SLOを置く。これは一件ごとの期限ではない。期限内に完了しない要求も破棄せず、完了するまで調停対象として残す。対象単位の達成率を継続的に集計する仕組みは初期リリース対象外とする。
- このSLOは、実際に非同期反映の対象になった単位を測る。通常配信では、配信時にホームタイムラインキャッシュが存在したフォロワーへの追加を一件とする。高ファンアウト経路では、投稿者のユーザータイムラインキャッシュへの反映を一件とする。初回昇格時は、各フォロワーの「閲覧時に合成する高ファンアウト投稿者」への追加を一件として別に測る。フォロー変更では、その利用者のホームタイムラインキャッシュへの反映を一件とする。キャッシュが無いホームタイムラインの利用者は次回閲覧時に原データから作り直すため、この5分SLOの分母に含めない。
- 高ファンアウト経路を使用する投稿者のポストは、投稿者のユーザータイムラインキャッシュへ反映し、フォロワーの閲覧時に合成する。Redis反映後にAlloyDBへ完了を記録し、完了が無い要求を調停処理がOutboxから再び処理することで反映を失わない。DLQ移動やPub/Sub保持期限を回復限界にしない。初回移行時の各フォロワーへの追加も未完了の対象を追跡し、定期的な作り直しへ回復を委ねない。
- ホームタイムラインの順序は、到着順や作成日時ではなくポストIDの降順で決定的に決める。通常ポストとユーザータイムライン経由のポストが異なる経路を通っても、同じ順序で統合する。
- 同じ配信処理が再実行されても、タイムラインキャッシュへの配置を重複させない。

## 負荷保護

利用者単位のレート制限と、投稿者単位の配信予算は別々に適用する。前者はAPIの操作回数、後者は一ポストから生じる配信量を制御する。

利用者ID・操作種別・時間窓ごとの暫定上限を同時に適用する。上限に達した操作は拒否し、利用者へ恒久的な属性を付けない。

| 操作 | 上限 |
|---|---|
| ポスト作成 | 5回/秒、60回/時、300回/日 |
| タイムライン閲覧（ユーザータイムライン取得とホームタイムライン取得の合計） | 10回/秒、120回/時 |
| フォローとフォロー解除の合計 | 20回/分、100回/日 |

認証前の大量通信は、送信元IP単位の粗い制限で別に抑える。この閾値は業務上の操作回数ではなく、観測後に決める。

投稿者単位には、同時実行数、発行中の配信単位数、配信先件数の予算を設ける。予算を超えたポストは拒否せず受け付け、その投稿者の配信待ちとして扱う。一人の投稿者が共有の配信処理能力を占有しない。

高ファンアウト投稿者を多くフォローしていても、読み取り時に合成する高ファンアウト投稿者を黙って減らさない。過負荷は次の方法で防ぐ。

- Redisから100キーずつ取得する。この件数は実装の定数であり、負荷試験の結果で見直す
- 最大5,000人の高ファンアウト投稿者をすべて処理し、黙って減らさない
- 直近キャッシュを使うページでは、各バッチを合成するたびに重複を除いた新しい側の最大51件だけを残す。キャッシュより古いページは原データから取得する
- 一リクエストが使えるデータ量とメモリ量を制限する
- APIインスタンス全体で、同時に実行する合成数を制限する

安全上限を超えた場合は、部分的なタイムラインを正常結果として返さない。過負荷エラーを返す。

### 一次データへの到達量の制限は、値が決まっていない

一リクエストのデータ量とメモリ量の上限、APIインスタンス全体の同時合成数の上限、キャッシュが止まったときに一次データへ流す量の上限は、具体的な値が決まっていない。値は負荷試験で決める（「まだ決まっていないこと」を参照）。

現在の実装で一次データへの到達量を抑えているのは、APIインスタンスごとの二つの接続プールの上限（`POSTGRES_WRITE_MAX_CONNS`と`POSTGRES_READ_MAX_CONNS`）と、Cloud Runの最大インスタンス数だけである。接続プールが埋まった要求は、空きを待つ。上限を超えた要求を過負荷エラーとして明示的に拒む仕組みは、まだ無い。

キャッシュ全体が無い場合の同期的な作り直しは、同じ利用者について同時に一つだけ進める。作り直し中に新しいポストまたはフォロー変更が成立した場合は、古い候補を公開せず現在の原データからやり直す。

## 信頼性

- ポストが作成されたのに配信が始まらない状態を作らない。ポストの作成と配信要求は同じトランザクションで確定する。
- 配信要求の発行は少なくとも一回とし、重複はタイムラインキャッシュ側で無害化する。
- 障害時は、ポスト受付と閲覧のどちらを継続しどちらを縮退するかを、次のとおり決めておく。

| 障害 | 継続する | 縮退・拒否する |
|---|---|---|
| 一次データが利用できない | なし | ポストとフォロー変更は成功扱いにしない。タイムラインキャッシュはポスト本文を持たず、本文を一次データから取得できない閲覧は失敗させる |
| 配信要求の発行が止まる | ポスト受付 | フォロワーへの反映が遅れる。復旧後に再開する |
| 非同期配信が止まる | ポスト受付、既存のユーザータイムラインとの合成 | 通常ポストのフォロワー反映とユーザータイムラインへの反映が遅れる。復旧後に冪等に再処理する |
| キャッシュが止まる | 一次データからの閲覧 | 一次データへの到達量を制限し、超過分は縮退または拒否する。現在の実装は接続プールの上限だけで抑え、明示的に拒む仕組みは無い。上限値は負荷試験で決める |
| レート制限の判定が止まる | 閲覧（プロセス内の上限で継続） | ポスト・フォロー・フォロー解除は安全側へ拒否する |

レート制限の判定が止まったときのプロセス内の上限は、平常時より小さい値にすることを求めているが、具体的な値は決まっていない。現在の実装は、共有のレート制限と同じ上限（タイムライン閲覧は10回/秒、120回/時）を、APIインスタンスごとに当てている。利用者の要求は複数のインスタンスへ振り分けられるため、サービス全体で通り得る回数は、平常時の上限にインスタンスの数を掛けたものになる。小さな上限の値は、負荷試験で決める。
| GoogleまたはClerkのログイン経路が止まる | 有効なセッションと検証可能な既知鍵を持つ登録済み利用者の業務API | 新しいログインと登録は成功扱いにせず、別IdPに切り替えない |
| Clerk Backend APIが止まる | 登録済み利用者は、保存済みのClerkユーザーIDと利用者IDのひも付けを使って業務APIを利用できる | GoogleアカウントIDを確認できない初回登録は拒否する |

## データの保持

- ホームタイムラインキャッシュは利用者ごとに0件から500件を保持する。500件はキャッシュ上限であり、フォロー解除後の件数不足を古いポストで補充しない。キャッシュより古い表示資格のあるポストは原データから読み取れる。経過時間による表示制限は設けない。
- ポストとフォロー関係の原データは、算定期間3年の累積を容量設計の仮定にする（業務上の期限ではない）。AlloyDBの論理量は、ポストの一次データ、本文を重ねて持つポスト作成履歴、フォロー変更履歴だけでも下限参考約6.76TBである。業務イベント共通ヘッダー、Outboxなどの技術状態、行オーバーヘッド、索引、複製、バックアップは別途加算する。タイムラインキャッシュはRedisに置き、利用者あたり最大500件で頭打ちになる。
- 長期間経過した現在状態データの物理削除、アーカイブ、匿名化、法的保全は初期リリースの対象外とする。成立した業務イベントのレコードは期間にかかわらず削除しない。
- 初期リリースでは、Outbox要求、回収、発行完了、配信のバッチ完了・範囲完了・要求全体完了、調停の回収・発行に関する全レコードを、完了済みか未完了かにかかわらず退避も削除もしない。
- 業務イベントのレコードは初期リリースに限らず、退避または削除の対象にしない。
- 未完了の要求は、古いことや試行回数、Pub/Subの保持期限、DLQへの移動を理由に破棄しない。5分間進捗が無いものを調停対象とし、要求成立から30分を超えて未完了のものを構造化Errorログの対象にする。
- ホームタイムラインの取得履歴は業務イベントとして保存しない。初期リリースでは構造化ログで失敗を確認し、取得量と遅延の集約メトリクスは対象外とする。

## セキュリティ

- 認証済み利用者は、Clerkが発行するセッションJWTの署名、発行者、audienceまたはauthorized party、有効期限をバックエンドが検証し、そのClerkユーザーIDにひも付くサービス内の利用者IDを得た利用者である。リクエストで自己申告された利用者IDを信頼しない。
- 利用者登録とログインはGoogleアカウントに限定する。専用Clerk instanceでGoogle以外の方法を無効にし、UI/APIはGoogle以外のstrategyを公開せず、初回JIT登録でClerk Backend APIから検証済みGoogle external accountとGoogleアカウントIDを確認する。標準JWTの検証成功だけでGoogle認証済みと断定しない。
- GoogleアカウントIDを、同じGoogleアカウントかを見分けるために使う。Clerk JWTの`iss`（Clerk環境）と`sub`（ClerkユーザーID）は現在のClerkユーザーの検証に使い、メールアドレスの一致でアカウントを統合しない。
- 署名検証済みclaimのキャッシュ期間は、設定TTLとtokenの`exp`までの残り時間のうち短い方を上限にする。
- Googleで本人確認できても、サービスへの利用者登録が完了していなければ、登録以外の業務APIを許可しない。
- 自分以外の利用者が自分と偽ってポストし、フォローし、フォローを外し、ホームタイムラインを見ることはできない。この境界は認証済みの主体と操作対象を照合して守る。
- 公開APIへの入口を一つに限定し、一次データとキャッシュへは私設経路だけで接続する。サービスごとに資格情報を分け、秘密情報は秘密管理の仕組みで扱う。
- JWT、GoogleアカウントID、メールアドレス、Clerk secretは通常ログとエラー応答へ出力しない。

## 運用性と観測

- ポストの作成と非同期配信の進行を区別して観測できる。
- 利用者別の制限超過、投稿者別の配信滞留、未発行の配信要求の件数と最古の経過時間、非同期配信の未処理件数と最古の経過時間を観測する。
- 未完了の技術状態が5分を超えたら遅延として扱い、30分を超えたら要求種別、要求ID、成立日時を構造化Errorログへ記録する。初期リリースでは外部通知先への配送は対象外とする。
- 一次データの自動バックアップとポイントインタイムリカバリを有効にする。
- 登録成功・拒否、JWT検証失敗の理由分類、認証済み未登録の拒否、Clerk Backend API失敗、Google以外の方法が有効になった設定ドリフトを、秘密情報を残さず観測できる。

## 移植性と開発環境

- バックエンドはGoで実装し、APIスキーマはProtocol Buffersで定義する。バックエンド間はgRPC、ブラウザ向けには同じ定義からgRPC-Webを提供する。
- 3〜6名程度のチームが変更しやすい構成にする。
- 開発者のラップトップとGitHub Codespacesで起動でき、ローカルではDocker ComposeでAPI、非同期処理、PostgreSQL、2用途のRedis、Pub/Subエミュレーターを本番と同じプロセス境界で起動できる。

## まだ決まっていないこと

- API応答時間とサービス可用性の目標値。負荷試験を行う段階で決める。回答責任者は利用者。
- 送信元IP単位の制限の閾値。プレビューモードの観測後に決める。
- 投稿者別配信予算の具体値（同時実行数、発行中の配信単位数、配信先件数）。負荷試験の入力として後続で決める。
- ホームタイムライン一回当たりのデータ量とメモリ量の上限。APIインスタンス全体の同時合成数と、キャッシュが止まったときに一次データへ流す量の上限も負荷試験で決める。現在の実装は接続プールの上限だけで抑えている
- レート制限の判定が止まったときのプロセス内の上限の値。現在の実装は平常時と同じ上限をインスタンスごとに当てており、全体ではインスタンスの数だけ倍になる
- キャッシュ全体が無い利用者の一斉閲覧で発生する同期的な作り直しについて、処理量と同時実行数の上限を負荷試験して決める
- Pub/Sub購読のメッセージ保持期間、デッドレター運用、未完了要求を調停する周期と一回の処理上限。
- Clerkの採用SDK/versionにおけるGoogleアカウントIDと検証済み状態の正確なfield。公式仕様と契約テストで確定する。
- 本人退会・同じGoogleアカウントによる再登録・強制退会は業務上の結果を合意済みだが、いずれも初期リリース対象外である。実装時の可用性、監査、運用の品質条件は未決。
- 強制退会からの復旧・異議申立て・Googleアカウントの付け替えと、それらに対応する保持・匿名化。
